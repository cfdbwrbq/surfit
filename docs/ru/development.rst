Разработка
==========

Структура репозитория
---------------------

.. list-table::
   :header-rows: 1
   :widths: 26 74

   * - Путь
     - Содержимое
   * - ``src/sstuff``
     - служебная библиотека: векторы, контейнеры, логирование, файловый ввод-вывод, потоки
   * - ``src/surfit``
     - движок: типы данных, функционалы, матричные операторы, решатели
   * - ``src/surfit_io``

   * - ``src/globe``, ``src/freeflow``

   * - ``src/tclsurfit``
     - интерфейс SWIG, превращающий функции движка в команды Tcl
   * - ``src/pysurfit``
     - привязки Python и их тесты
   * - ``examples``
     - примеры на Tcl и регрессионный набор
   * - ``doc``
     - исходники Doxygen; ``docs`` — эта документация на Sphinx

Как устроены привязки
---------------------

Публичный API движка — это набор свободных функций C++. SWIG читает
``src/tclsurfit/src/*.i`` и генерирует по команде Tcl на каждую функцию;
привязки Python вызывают те же самые функции напрямую через pybind11.

Поэтому фронтенды не могут разойтись: второй реализации чего-либо просто нет.
По той же причине слой привязок тонкий — работа состоит в переводе соглашений
об аргументах и результатах, а не в повторной реализации поведения.

pybind11 выбран вместо нацеливания SWIG на Python потому, что привязкам нужно
передавать буферы numpy и возбуждать исключения Python вместо возврата кодов
ошибки Tcl.

Отдельная аккуратность нужна там, где движок встречается с плагином. И
``libsurfit``, и ``libsurfit_io`` определяют вспомогательные структуры, и две
из них раньше носили одно имя. Поскольку теперь обе библиотеки линкуются в
один модуль, такая коллизия разрешается динамическим линкером молча и
вызывается чужая реализация; поэтому копии в плагине получили суффикс ``_io``.
Прежде чем линковать ещё одну библиотеку, сравните экспортируемые символы:

.. code-block:: bash

   nm -DC --defined-only bin/libsurfit.so | sed 's/^[0-9a-f]* [A-Za-z] //' | sort -u > /tmp/a
   nm -DC --defined-only bin/libsurfit_io.so | sed 's/^[0-9a-f]* [A-Za-z] //' | sort -u > /tmp/b
   comm -12 /tmp/a /tmp/b

Встроенные методы из общих заголовков попадут в оба списка и безвредны: их
определения совпадают. Обычное имя типа, встретившееся в обоих, — нет.

Две библиотеки плагинов разделены так же, как форматы. ``libglobe_core`` и
``libfreeflow_core`` содержат код и не зависят от Tcl; ``libglobe.so`` и
``libfreeflow.so`` — Tcl-плагины, собранные из файлов ``*_wrap.cxx``,
сгенерированных SWIG 1.3.28. Python линкуется с основными библиотеками,
поэтому колесо несёт их с собой, а ``import surfit`` регистрирует их менеджеры
данных — то же самое, что делает ``load libglobe.so`` под Tcl. Перед тем как
линковать их с движком, сравните экспортируемые символы: проверка выше
подходит без изменений.

Тестирование
------------

.. list-table::
   :header-rows: 1
   :widths: 34 66

   * - Команда
     - Что она устанавливает
   * - ``./run_baseline.sh``
     - исходный Tcl-фронтенд по-прежнему проходит все 35 регрессионных скриптов
   * - ``python3 src/pysurfit/tests/run_tcl_suite.py``
     - те же скрипты, переведённые в вызовы привязок, дают побайтово
       совпадающие файлы данных
   * - ``... run_tcl_suite.py --sequential examples/surfit/realworld``
     - то же для 29 скриптов на реальных данных, с учётом конвейеров
   * - ``python3 src/pysurfit/tests/test_examples.py``
     - каждый пример Python из ``examples/python`` запускается так, как его
       запустит читатель, и пишет тот же ``.dat``, что и его Tcl-оригинал,
       побайтово; Tcl-скрипт без порта валит проверку, если только он не
       перечислен как намеренно непереносимый
   * - ``python3 src/pysurfit/tests/test_parity.py``
     - сохранённый файл совпадает с Tcl-версией, ``values()`` совпадает с
       блоком коэффициентов внутри этого файла, а массив переживает круговой
       рейс
   * - ``python3 src/pysurfit/tests/test_all_commands.py``
     - каждая команда обоих фронтендов, включая плагины, прогоняется через оба
       из одной таблицы; значения, предупреждения и записанные файлы должны
       совпасть, а сам список команд читается из tclsh, поэтому команда, которой
       нет в Python, не может остаться незамеченной
   * - ``python3 src/pysurfit/tests/check_stringmatch.py``
     - локальный сопоставитель имён совпадает с Tcl на всех корректных шаблонах
   * - ``python3 gil_check.py``
     - решение действительно отпускает GIL
   * - ``python3 stress_check.py``
     - повторные прогоны в одном процессе не текут

Прогонщик умеет также проверять сборку, в которой Tcl-фронтенда нет вообще.
Сторона Tcl запускается один раз, её вывод сохраняется, а последующие прогоны
сравнивают с этим эталоном сторону Python:

.. code-block:: bash

   python3 src/pysurfit/tests/run_tcl_suite.py --sequential \
       --save-references refs examples/surfit/realworld     # с Tcl
   python3 src/pysurfit/tests/run_tcl_suite.py --sequential \
       --use-references refs examples/surfit/realworld      # без Tcl

Сопоставление имён
------------------

Объекты выбираются по имени с шаблонами, и движок реализует сопоставление сам.
Раньше он вызывал ``Tcl_StringMatch`` — это была последняя связь ядра с Tcl.

Правила сняты с самого Tcl, а не угаданы, и
``src/pysurfit/tests/check_stringmatch.py`` сравнивает реализации на нескольких
тысячах пар шаблон и строка, включая ``[]]``, обратные диапазоны вроде ``[c-a]``
и экранирование:

* ``*`` и ``?`` ведут себя как ожидается;
* диапазон совпадает в любую сторону, поэтому ``[c-a]`` соответствует ``a``,
  ``b`` и ``c``;
* ``]`` сразу после ``[`` закрывает множество, так что ``[]]`` — пустое
  множество;
* ``!`` и ``^`` — обычные символы: в ``string match`` у Tcl нет отрицания;
* внутри множества нет экранирования: обратная косая черта такая же участница,
  как и любая другая.

Шаблоны с **незакрытой** ``[`` из этого сравнения исключены. Ответ Tcl там
зависит от памяти после строки: ``string match {a[b} {ab}`` возвращает 1 сам по
себе и 0, если после него была выделена другая строка. Локальный сопоставитель
выбирает детерминированное прочтение — множество тянется до конца шаблона, — и
именно это Tcl возвращает в обычном случае.

Непрерывная интеграция
----------------------

``ci/check.sh`` собирает всё с нуля в ``build-ci`` и прогоняет все проверки: 35
тестовых скриптов со сверкой Tcl и Python рядом, 49 примеров Python против их
Tcl-оригиналов, паритет, сопоставление имён против Tcl, две задачи в одном
процессе, вьюер, документацию (сверку двух деревьев между собой и сборку каждого
языка без предупреждений, если установлен Sphinx) и колесо, которое ставится в
изолированный каталог и считает там без ``LD_LIBRARY_PATH``.

Это занимает около двадцати минут — такова цена сверки с Tcl-фронтендом, а не с
самим собой. ``ci/check.sh --full`` добавляет 29 realworld-конвейеров, ещё час, и
именно это запускает ночная задача.

GitHub Actions вызывает ровно этот скрипт, поэтому на push выполняется то же
самое, что можно запустить руками. Windows и MSVC не покрыты.

Иллюстрации в документации
--------------------------

Карты в разделе «Готовые примеры» — это настоящий результат,
зафиксированный в виде SVG, чтобы для сборки документации не требовались ни
node, ни браузер. Рисует их тот же ``surfit/viewer.js``, что и страницу, поэтому
иллюстрация не может разойтись с тем, что выдаёт ``save_viewer()``. Пересобрать
их можно через ``docs/make_images.py`` после изменения вьюера или примера; для
этого нужны node, d3 и jsdom.

Справочник команд
-----------------

Страница «Справочник команд» не пишется руками, а генерируется:
``docs/make_command_reference.py`` берёт список команд из интерфейсных файлов
SWIG в ``src``, а синтаксис, описание, параметры и примеры — из комментариев
Doxygen в заголовках. ``docs/check_docs.py`` падает, если страница устарела,
поэтому новая команда или правка заголовка не могут оставить справочник
позади. Имена команд и описания в обеих ветках одинаковы; переводятся только
заголовок и вступление.

Почему побайтовое равенство
---------------------------

Неверный результат не всегда приводит к ошибке. Во время портирования
отсутствующая подстановка обратной косой черты заставила загрузчик неверно
прочитать колонки; решение после этого выдало поверхность из значений ``nan`` —
без ошибки, без предупреждения и с файлом ровно того же размера. Именно
сравнение с эталоном побайтово это и поймало, и с тех пор оно ловит все тихие
расхождения.

Скрипты, которым нужна непривязанная команда, помечаются как ``SKIP`` с именем
этой команды. Покрытие всегда указывается числом, никогда — словами «всё
хорошо».

Почему решатель остаётся на C++
-------------------------------

Отдельный прототип повторил основную задачу на numpy/scipy: ту же систему
``d1·D1 + d2·D2``, те же пятиточечные и четвёртого порядка шаблоны, ту же
лестницу сеток, прямой решатель и сопряжённые градиенты. Это измерительный
инструмент, а не второй движок.

Формулировка воспроизводится. Семь точек и completer сходятся с движком до
``4·10⁻⁵`` диапазона значений при ``tol=1e-8``, поверхность-данные — до
``10⁻¹⁵``, а запись ``.dat`` проходит побайтово. Скорость — нет: прямое
решение конкурентно только примерно до 160×160 (81×81: 0.15 с против 0.31 с;
161×161: 1.0 с против 0.68 с), на 321×321 — 6.7 с против 1.4 с, а на 641×641
разреженная факторизация уже не влезает, тогда как движку нужно 2.2 с.
Сопряжённые градиенты на numpy/scipy в 20–130 раз медленнее (около 10 мс на
итерацию против 0.1 мс на 321×321; 290 с против 2.2 с на 641×641). Штрафные
циклы (``mean``, ``wmean``, ``ineq``) останавливаются по изменению нормы
решения, а не по невязке, и при ``tol=1e-6`` из примеров оставляют 14–21%
диапазона; при ``1e-10`` они совпадают с точным решением штрафной задачи.

Поэтому прототип остаётся эталоном и песочницей, а не заменой. Повторить 35
классов функционалов, CMOFS и менеджеры данных значило бы завести вторую
семантику, которую пришлось бы держать в синхроне, — и без выигрыша в
скорости. Те же замеры полезны самому движку: ``tol`` — это шаг CG, а не
граница ошибки (см. известные проблемы ниже), а штрафным циклам нужно условие
остановки по невязке.

Известные проблемы
------------------

* **Одно активное состояние.** Сессия подставляет своё состояние перед каждым
  вызовом — на этом и держится работа двух задач в одном процессе; но сама
  подстановка не защищена, поэтому две сессии нельзя вести из двух потоков
  одновременно. Thread-local хранилище тоже не помогло бы: рабочие потоки
  решателя читают те же глобалы.
* **Плагин линкуется целиком.** ``libsurfit_io`` стоило бы собирать со скрытой
  видимостью и экспортировать только публичный API, вместо того чтобы
  полагаться на несовпадение имён вспомогательных структур.
* ``surf_plot`` по-прежнему пишет PostScript через CreEPS для Tcl-фронтенда. В
  Python он не привязан — там вывод закрывает вьюер.
* **``tol`` — не граница ошибки.** CG останавливается по ``max|alpha·p|``,
  поэтому при ``tol=1e-6`` результат может уйти примерно на 0.7% диапазона
  значений; штрафные циклы (``mean``, ``wmean``, ``ineq``) останавливаются по
  изменению нормы и при том же допуске оставляют 14–21%. Сравнивайте решения
  по невязке или берите допуск заметно ниже нужной точности.

Работа над проектом
-------------------

В проекте ведётся каталог ошибок и выведенных из них правил —
``.agents/skills/error-to-skill/LESSONS.md`` — вместе с практикой, которая его
порождает. Прочитайте его перед работой над затронутой там подсистемой и
дополняйте после любой нетривиальной неудачи.

Лицензия
--------

surfit — свободное программное обеспечение под GNU General Public License

Один файл под эту лицензию не подпадает. ``src/surfit/src/triangle.cpp`` — это

триангуляцию.
